# مخطّط قاعدة البيانات — سوق تاجر

هذا المجلّد يحفظ نسخة من مخطّط قاعدة البيانات داخل المشروع (version control).

> **مهم:** رفع الملف إلى GitHub **لا يطبّقه** على Supabase.
> GitHub يحفظ الملف فقط. التطبيق يتم يدوياً من لوحة Supabase (انظر أدناه).

---

## الملفات

| الملف | الوصف |
|---|---|
| `001_marketplace.sql` | جداول السوق: البائعون · المنتجات · الطلبات · الإحالة · التحويلات + سياسات RLS |

---

## كيفية التطبيق

1. افتح [لوحة Supabase](https://supabase.com/dashboard) واختر المشروع.
2. من القائمة الجانبية: **SQL Editor** ← **New query**.
3. انسخ محتوى `001_marketplace.sql` كاملاً والصقه.
4. اضغط **Run**.
5. النتيجة المتوقّعة: `Success. No rows returned`.

### قبل التطبيق على قاعدة الإنتاج

الملف يفعّل RLS على جدول `profiles` الموجود مسبقاً ويسحب صلاحية `UPDATE`
المباشرة منه. **إذا كان كود الواجهة يعدّل `profiles` من المتصفّح، سيتوقّف.**
كل تعديل على `is_admin` أو `pro_until` أو `tier` يجب أن يمرّ عبر
Edge Function بمفتاح `service_role`.

الأسلم: أنشئ **Branch** من تبويب Branches وجرّب عليه أولاً،
أو خذ نسخة احتياطية من Database ← Backups.

## ما بعد التطبيق: Storage

من لوحة Supabase ← **Storage**، أنشئ حاويتين:

| الاسم | public | الاستعمال |
|---|---|---|
| `product-files` | ❌ لا | ملفات المنتجات المدفوعة |
| `seller-media` | ✅ نعم | صور البائعين والأغلفة |

ملف المنتج المدفوع **لا يُسلَّم أبداً برابط مباشر** — فقط رابط موقّع
قصير الأجل يولّده Edge Function بعد التحقّق من أن الطلب مدفوع.

## نموذج تقسيم الأرباح

على بيع بـ 1000 دج:

| الطرف | النسبة | المبلغ |
|---|---|---|
| البائع | 70% | 700 دج |
| المُحيل | 10% | 100 دج |
| المنصّة | 20% | 200 دج |

عمولة الإحالة **تُخصم من حصة المنصّة، لا تُضاف فوقها**.
إذا لم يوجد مُحيل، تحصل المنصّة على 30% كاملة.

المبالغ تُجمَّد في الطلب وقت الشراء (snapshot)، فتغيير نسبة العمولة
لاحقاً لا يؤثّر على الطلبات القديمة.

## الإحالة

كل بائع معتمد له `ref_code` ورابط لافتة جاهز في العرض `sellers_public`:

```
page_url  → https://tajer-app.vercel.app/s/<slug>
badge_url → https://tajer-app.vercel.app/?ref=<ref_code>&src=badge
```

اللافتة توضع أسفل صفحة كل بائع. أي زائر يدخل منها ثم يسجّل، يُنسب
لذلك البائع لمدة **30 يوماً** (`attribution_ends_at`).

### ضوابط مكافحة الاحتيال المدمجة

- منع الإحالة الذاتية عبر محفّز `referrals_no_self` (على مستوى قاعدة البيانات)
- تجميد **14 يوماً** قبل استحقاق التحويل (`payout_eligible_at`)
- تجزئة الـ IP والجهاز (`ip_hash` / `device_hash`) — لا تُخزَّن خاماً
- عمود `flagged` للمراجعة اليدوية

## الجداول

| الجدول | الوصف |
|---|---|
| `sellers` | البائعون · slug الصفحة · نسبة العمولة · بيانات التحويل |
| `digital_products` | المنتجات · الأسعار · حالة المراجعة |
| `orders` | الطلبات بمبالغ مجمّدة · رموز التحميل |
| `referral_clicks` | نقرات اللافتة |
| `referrals` | الإسناد بعد التسجيل |
| `payouts` | سجلّ التحويلات اليدوية (CCP / BaridiMob) |

### العروض (Views)

| العرض | مَن يقرأه |
|---|---|
| `sellers_public` | الجميع — أعمدة آمنة فقط، بلا بيانات دفع |
| `seller_balances` | البائع — رصيده المستحق والمجمّد وأرباح إحالته |
| `platform_revenue` | الإدارة فقط — ملخّص شهري |

## ملاحظات أمنية

- جدول `sellers` **مغلق تماماً** أمام القراءة العامة لأنه يحوي CCP/BaridiMob.
  الواجهة تقرأ من `sellers_public` حصراً.
- لا توجد أي سياسة كتابة على `orders` من المتصفّح. إنشاء الطلبات
  وتأكيد الدفع يتمّان حصراً من Edge Function بمفتاح `service_role`.
- البائع لا يستطيع: رفع عمولته · الموافقة على منتجه · تزوير عدّاد
  المبيعات · رؤية طلبات غيره أو بيانات دفعه.
- تعديل منتج معتمد (العنوان/السعر/الملف/الوصف) يعيده تلقائياً
  إلى `pending` للمراجعة.
- التحقّق من الإدارة يتم عبر `public.is_admin()` من قاعدة البيانات،
  لا من الواجهة.

مع محاولات تجاوز صلاحيات. النتائج:

- تقسيم بيع 2000 دج: 1400 / 200 / 400 ✅
- العدّادات وفترة التجميد ورمز التحميل تُضبط تلقائياً ✅
- رفض: الإحالة الذاتية · رفع العمولة · الموافقة الذاتية · تزوير المبيعات ✅
- عزل كامل بين البائعين، ومنع الزائر من جدول الطلبات ✅
